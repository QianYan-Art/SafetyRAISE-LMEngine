# SafetyRAISE-LMEngine 架构与重构约束

## 目标与来源

本项目从服务 SafetyRAISE 专家小模型的 Rust Qwen3 推理实现，演进为面向本地部署的 Qwen 系列推理框架。专家指导、事故信息提取与报告生成使用同一运行时合同，模型数学、权重表示和设备执行分别演进。Rust 负责资源所有权、请求生命周期和服务；可选性能算子通过明确的 ABI 接入，不能绕过模型状态和错误边界。

这次重构交付模型加载、请求服务、可复现的边界验证和维护文档。目标包括 Qwen2/Qwen3 稠密模型、Qwen3.5 混合注意力、量化权重、状态恢复、思考预算、工具交互、视觉输入和 MTP。接口存在不等于模型路径已完成；配置解析成功也不等于真实权重生成已通过。

## 分层与所有权

1. **模型资源**：解析 safetensors/GGUF 元数据、张量布局、tokenizer 与模板；按 `model_type`、架构及层类型校验形状和功能。发行名不决定计算图。
2. **模型执行**：Qwen2/Qwen3 稠密 Transformer 与 Qwen3.5 混合注意力分别实现数学。只读权重与每请求状态分离；视觉塔和 MTP 具有独立的权重与状态合同。
3. **算子后端**：CPU 是正确性基线；`native` 使用受能力检查保护的 C ABI；`wgpu-q8` 当前提供 Q8 线性操作和必要的回退。旧顶层调试入口保留一条 Qwen3 resident decode 实验链，该链与新服务后端分开统计。
4. **请求运行时**：有界队列、分块 prefill、逐步 decode、取消、超时、资源预算与可选 prefix cache。先提交模型状态，再发布输出；失败或取消释放资源。
5. **前端与服务**：tokenizer、聊天模板、思考/正文/工具分流、停止条件、工具消息、图像占位符及有限 OpenAI 风格 HTTP/SSE。`serve` 与 `run` 共用服务链；业务中的事故信息字段和报告审查策略由 SafetyRAISE 主系统拥有，不固化进算子。

## 部署入口

`rsinfer serve/run/inspect/benchmark` 是当前统一入口。`serve` 加载 `ServiceConfig` 并暴露有限 HTTP/SSE；`run` 执行同一链路的单个 JSON 请求；`inspect` 只读解析权重和状态预算；`benchmark` 对指定真实配置和请求输出实验元数据。配置路径、模板覆盖、认证和请求示例见 [部署与服务配置](deployment.md)。

旧的顶层参数入口仍用于本机 Qwen3 调试和 profile。它可选择 `cpu`、`auto`、`hybrid`、Q8 及实验性 resident decode。旧 resident 链包含更宽的 decode 前缀驻留逻辑；服务中的 `wgpu-q8` 只声明线性/Q8 能力，不能据此推断服务已经拥有旧链的 resident 行为。

## 必须保持的不变量

- 入场前按实际 tokenizer 计算输入、可生成 token、思考强制收束与上下文余量；拒绝不合法请求，不能静默截断事故材料。
- 模型参数、tokenizer、模板、适配器、位置配置与状态类型共同决定缓存兼容性；不能只按相同文本复用缓存。
- 全注意力 KV 可截断不代表 GDN 状态可截断。混合模型恢复点必须包含卷积历史、递归矩阵、位置、已提交 token 与所选草稿状态。
- MTP 只对满足条件的 greedy、纯文本请求启用；提议 token 必须经过完整目标分布验证。停止、取消和回滚不能发布未接受 token。开启 MTP 不构成加速承诺。
- 单次请求与并发请求各自承担资源上限；权重、缓存、运行工作区和保留余量分别核算，不把总显存全部分配给权重。
- CUDA/AVX 等能力依据设备与实际可用内核选择；当前仓库未宣称 CUDA 插件已编译，也不能用编译成功代替 Orin、SM86 或其他硬件验收。
- 正确性证据、协议证据、真实权重验证与实机性能证据分别记录；不声称未经测试的速度优势或生产成熟度。

## 资源边界

`ServiceConfig` 对请求体、输出、视觉 token 和 GPU 预算设上限；`EngineConfig` 进一步限制上下文、并发、队列、prefill 分块、事件背压、工作内存、prefix cache 和请求超时。CLI 配置文件读取上限为 1 MiB，HTTP/`run` 请求由 `max_body_bytes` 约束（默认 8 MiB、最大 64 MiB）；旧 Qwen3 配置读取器对 Hugging Face `config.json` 设 2 MiB 上限，统一服务的权重清单读取另有独立限制。外部 chat template 限制为 1 MiB。视觉请求最多四张图像，并按字节、像素、patch 和 merged token 分别核验。

## 历史经验如何进入实现

| 既有经验 | 本次工程要求 |
| --- | --- |
| 本机 Q8 驻留减少同步，但 CPU prefill 和主机往返仍限制速度 | 保留旧调试路径，服务后端按实际线性能力单独记录传输与回退 |
| 工作站 Bonsai 使用特殊三元格式，普通后端不能直接加载 | 明确量化格式支持，不将所有 GGUF 解释为相同低比特布局 |
| Orin 同时有全注意力 KV 与 GDN 递归状态 | 统一请求状态所有权，恢复和投机事务覆盖两类状态 |
| 5120 思考预算与 32768 窗口导致长报告截断 | token 预算入场检查、输出停止原因与预算指标可见 |
| MTP 词表子集收益与并发草稿长度相关 | 草稿预算受活跃请求与验证容量约束，保留完整目标验证，不宣称必然加速 |
| 单路测速改善没有证明整条报告链更快 | 实机验收时分开记录 prefill、decode、TTFT、排队与端到端；不混用不同工作负载 |
| 训练链路曾与线上协议不一致 | 服务契约与主系统独立核对，不能以旧评测成绩替代新协议验证 |
